• I have the relevant helper now. The short version is that these widths are counts of feature dimensions in the column output vector, and each shell
  owns a contiguous slice of that vector.

─────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────

• Those shell widths are feature dimensions on the column output vector, not pixels, examples, weights, or physical columns.

  In the current run, each column emits a tensor shaped roughly:

  (batch, tokens, embed_dim)

  With --embed_dim 64, the last axis has 64 scalar feature slots. The four shell widths split those 64 slots into contiguous slices:

  hard_kernel:  slots  0..21   width 22
  inner_shell:  slots 22..28   width 7
  middle_shell: slots 29..42   width 14
  outer_shell:  slots 43..63   width 21

  So the printed values:

  hard_kernel=22, inner_shell=7, middle_shell=14, outer_shell=21

  mean “how many scalar embedding channels each shell owns per token, per column.”

  The code computes this in columnarCL-fabricPC-experiments/columnar_cl_fabricpc/columns/depth_spanning_column.py:93. It uses default relative shell
  proportions:

  hard_kernel : inner_shell : middle_shell : outer_shell = 32 : 10 : 20 : 30

  Then it scales those proportions to embed_dim=64 and rounds so the four widths sum exactly to 64. The training script prints them from
  get_shell_slices(args.embed_dim) in columnarCL-fabricPC-experiments/scripts/train_cifar10_depth_spanning.py:1837.

  Expanding from 4 columns to 10 columns does not change those per-column shell widths. It means there are now 10 separate column outputs, and each
  one has the same 64-dimensional shell layout. In the shell-preserving composer, each (column, shell) component gets its own shell-local projection,
  for example hard-kernel projections are 22 x 22, middle-shell projections are 14 x 14, and so on.

  Shell lesion results show the learned classifier depends strongly on shell structure. Dropping hard_kernel hurts every seed badly; dropping
  outer_shell also hurts. In seed 7, dropping middle_shell is also catastrophic. That is encouraging because it means the shell layout is
  behaviorally load-bearing rather than decorative.

  Recommendation
  Next, I would run an isolation sweep before changing architecture:

  1. Same architecture, no teachers, outer context on.
  2. Compare shell_lr_multipliers=1,1,1,1 against 1,1.5,2,3.
  3. Use seeds 42, 99, and 7.

  Reason: we do not yet have a clean three-seed no-teacher outer-context baseline with flat shell learning rates. The current results are very
  promising, but to know whether the gain is from shell plasticity rather than outer context plus no teacher, we need that control. After that, I
  would sweep gentler/stronger shell plasticity profiles.
