     85 +stem ConvNode
     86 +    |
     87 +    v
     88 +ResNet-style predictive-coding backbone
     89 +    |
     90 +    +--> stage2_out ----> stage2_tap ----+
     91 +    |                                     |
     92 +    +--> stage3_out ----> stage3_tap ----+--> col_00 --+
     93 +    |                                     |             |
     94 +    +--> stage4_out ----> stage4_tap ----+--> col_01 --+
     95 +    |                                     |             |
     96 +    +--> stage4_out ----> stage4_pool ---+--> col_02 --+--> combiner --> column_pool --> output
     97 +                                          |             |                         |          ^
     98 +                                          +--> col_03 --+                         |          |
     99 +                                                                                v          |
    100 +                                                                    column_teacher_output   |
    101 +                                                                                           |
    102 +per-column shell readout and bridge paths ------------------------------------------------+
    103 +```
    104 +
    105 +The main classifier is `output`. In recent runs without `--bypass_columns`, the main classifier receives:
    106 +
    107 +- `column_pool -> output`
    108 +- each active per-column shell pool directly into `output`
    109 +- each active per-column shell bridge into `output`
    110 +
    111 +The column teacher node exists in the graph as `column_teacher_output`, but recent shell dynamics runs set `--column_teacher_weight 0.0`. That means its weighted
         cross-entropy energy is zero in those runs.
    112 +
    113 +## ResNet-Style Backbone
    114 +
    115 +The backbone is constructed by `make_residual_block()` and `build_depth_spanning_graph()` in `scripts/train_cifar10_depth_spanning.py`.
    116 +
    117 +For `resnet18`, the model configuration is:
    118 +
    119 +```text
    120 +stem_channels = 32
    121 +stage 1: channels=32,  blocks=2, first_stride=1
    122 +stage 2: channels=64,  blocks=2, first_stride=2
    123 +stage 3: channels=128, blocks=2, first_stride=2
    124 +stage 4: channels=256, blocks=2, first_stride=2
    125 +```
    126 +
    127 +The backbone node pattern is:
    128 +
    129 +```text
    130 +prev
    131 + |\
    132 + | \ if shape changes or stride > 1
    133 + |  \
    134 + |   v
    135 + |  skip projection ConvNode
    136 + |
    137 + v
    138 +conv_a ConvNode
    139 + |
    140 + v
    141 +conv_b ConvNode
    142 + |
    143 + v
    144 +skip_sum SkipConnection
    145 + ^
    146 + |
    147 +prev or skip projection
    148 +```
    149 +
    150 +`ConvNode` comes from upstream FabricPC. It computes a convolutional `pre_activation`, applies the configured activation, computes `error = z_latent - z_mu`, and
         stores Gaussian energy by default. Its fan-in for muPC scaling is `input_channels * product(kernel_size)`.
    151 +
    152 +`SkipConnection` comes from upstream FabricPC. It sums its inputs without learnable parameters and marks its input slot as not variance-scalable so muPC does not
         attenuate identity residual paths.
    153 +
    154 +The current depth-spanning columns use the last three backbone stage outputs:
    155 +
    156 +```text
    157 +stage2_out = stage_outputs[-3] = (16, 16, 64)
    158 +stage3_out = stage_outputs[-2] = (8, 8, 128)
    159 +stage4_out = stage_outputs[-1] = (4, 4, 256)
    160 +target_grid = (4, 4)
    161 +num_tokens = 16
    162 +```
    163 +
    164 +These values are printed by `build_depth_spanning_graph()` when the graph is built.
    165 +
    166 +## Stage Taps
    167 +
    168 +`StageTapTokenizer` converts a spatial backbone tensor into a common token tensor. In code, the transformation is:
    169 +
    170 +```text
    171 +(batch, height, width, channels)
    172 +    -> adaptive average pool to target_grid
    173 +    -> reshape to (batch, tokens, channels)
    174 +    -> multiply by W_proj and add b_proj
    175 +    -> add pos_embed if enabled
    176 +    -> optionally apply LayerNorm
    177 +    -> z_mu for the stage tap node
    178 +```
    179 +
    180 +The implementation is in `columnar_cl_fabricpc/columns/stage_taps.py`.
    181 +
    182 +The current graph creates:
    183 +
    184 +```text
    185 +stage2_out (16, 16, 64)  -> stage2_tap (16, 64)
    186 +stage3_out (8, 8, 128)  -> stage3_tap (16, 64)
    187 +stage4_out (4, 4, 256)  -> stage4_tap (16, 64)
    188 +stage4_out (4, 4, 256)  -> stage4_pool (1, 64)
    189 +```
    190 +
    191 +`GlobalPoolNode` computes `stage4_pool`. Its transformation is:
    192 +
    193 +```text
    194 +(batch, height, width, channels)
    195 +    -> mean over height and width
    196 +    -> multiply by W_proj and add b_proj
    197 +    -> expand to (batch, 1, embed_dim)
    198 +    -> optionally apply LayerNorm
    199 +    -> z_mu for stage4_pool
    200 +```
    201 +
    202 +In recent runs, `--layer_norm_tokens --fix_ln_gamma` makes each stage tap and `stage4_pool` use scalar gamma `1.0` and beta `0.0`, not learned LayerNorm gain and
         bias.
    203 +
    204 +## Depth-Spanning Column Inputs
    205 +
    206 +Each column has four single-input slots:
    207 +
    208 +```text
    209 +stage2      receives stage2_tap
    210 +stage3      receives stage3_tap
    211 +stage4      receives stage4_tap
    212 +stage4_pool receives stage4_pool
    213 +```
    214 +
    215 +The graph repeats this edge pattern for every column:
    216 +
    217 +```text
    218 +stage2_tap  -> col_XX:stage2
    219 +stage3_tap  -> col_XX:stage3
    220 +stage4_tap  -> col_XX:stage4
    221 +stage4_pool -> col_XX:stage4_pool
    222 +```
    223 +
    224 +The relevant code is `build_depth_spanning_graph()` in `scripts/train_cifar10_depth_spanning.py`, where `create_depth_spanning_column()` is called for each `idx`
         and the four edges are added.
    225 +
    226 +## Inside One Depth-Spanning Column
    227 +
    228 +Each column maps the four inputs to `(batch, tokens, embed_dim)`. For recent runs, this is `(batch, 16, 64)`.
    229 +
    230 +The internal computation is:
    231 +
    232 +```text
    233 +                 stage4_tap
    234 +                    |
    235 +                    +--------------------+
    236 +                    |                    |
    237 +                    v                    v
    238 +             K_deep path             L_deep path
    239 +                    |                    |
    240 +stage3_tap -------->+                    v
    241 +                    |              depthwise 3x3 conv
    242 +                    v                    |
    243 +              K_mid path                 v
    244 +                    |                 L_out
    245 +stage2_tap -------->+
    246 +                    |
    247 +                    v
    248 +                 K_out
    249 +
    250 +stage4_pool
    251 +    |
    252 +    v
    253 +B_deep -> B_out -> broadcast over all tokens
    254 +
    255 +K_out, L_out, and B_out each have shape (batch, tokens, embed_dim).
    256 +They are sliced into hard_kernel, inner_shell, middle_shell, and outer_shell.
    257 +```
    258 +
    259 +The K, L, and B paths are implemented in `DepthSpanningColumnNode.forward()`:
    260 +
    261 +- `K`: `stage4 -> K_W_deep -> concat(stage3) -> K_W_mid -> concat(stage2) -> K_W_out`.
    262 +- `L`: `stage4 -> L_W_deep -> reshape to grid -> 3 by 3 depthwise convolution -> L_W_out`.
    263 +- `B`: `stage4_pool -> B_W_deep -> B_W_out -> broadcast to every token`.
    264 +
    265 +The learnable parameters are initialized in `DepthSpanningColumnNode.initialize_params()`:
    266 +
    267 +```text
    268 +K_W_deep: input_dim -> microcolumn_dim
    269 +K_W_mid:  microcolumn_dim + input_dim -> microcolumn_dim
    270 +K_W_out:  microcolumn_dim + input_dim -> output_dim
    271 +
    272 +L_W_deep:    input_dim -> microcolumn_dim
    273 +L_W_conv_dw: 3 by 3 depthwise convolution over microcolumn_dim channels
    274 +L_W_out:     microcolumn_dim -> output_dim
    275 +
    276 +B_W_deep: input_dim -> microcolumn_dim
    277 +B_W_out:  microcolumn_dim -> output_dim
    278 +```
    279 +
    280 +## Column Shell Layout
    281 +
    282 +The column output feature axis is partitioned into four named slices:
    283 +
    284 +```text
    285 +feature axis, embed_dim = 64
    286 +
    287 +0                                                           64
    288 +|----------------------|-------|--------------|-------------|
    289 + hard_kernel            inner   middle_shell   outer_shell
    290 + width 22               width 7 width 14       width 21
    291 +```
    292 +
    293 +The default proportions are `32:10:20:30`. For `embed_dim = 64`, `compute_shell_sizes()` produces widths `22, 7, 14, 21`.
    294 +
    295 +The shell order is fixed in `SHELL_NAMES`:
    296 +
    297 +```text
    298 +hard_kernel -> inner_shell -> middle_shell -> outer_shell
    299 +```
    300 +
    301 +This ordering matters for feature slicing, same-tier inhibition, shell readout nodes, and outward shell evidence cascade.
    302 +
    303 +## Shell-To-Path Mask
    304 +
    305 +Each shell receives a fixed subset of K/L/B pathway evidence. The active subset is encoded in `DEFAULT_SHELL_PATH_MASK`.
    306 +
    307 +```text
    308 +                 K        L        B
    309 +hard_kernel      1        0        0
    310 +inner_shell      1        1        0
    311 +middle_shell     1        1        1
    312 +outer_shell      0        1        1
    313 +```
    314 +
    315 +The learnable `shell_path_scale` matrix has the same shape. The forward pass multiplies it by the fixed mask before combining K/L/B slices. A masked entry stays z
         ero in the forward computation even though `shell_path_scale` itself is a parameter tensor.
    316 +
    317 +For one shell slice, the computation is:
    318 +
    319 +```text
    320 +shell_output =
    321 +    shell_path_scale[shell, K] * K_out_shell
    322 +  + shell_path_scale[shell, L] * L_out_shell
    323 +  + shell_path_scale[shell, B] * B_out_shell
    324 +```
    325 +
    326 +The hard kernel receives only K pathway output. The outer shell receives only L and B pathway output.
    327 +
    328 +## Same-Tier Inhibition
    329 +
    330 +Same-tier inhibition is implemented in `_same_tier_inhibition()` and `_apply_pathway_shell_inhibition()` in `columnar_cl_fabricpc/columns/depth_spanning_column.py
         `.
    331 +
    332 +It is applied separately to each shell slice inside each of K, L, and B before shell-path mixing:
    333 +
    334 +```text
    335 +K_out -> split by shell -> inhibit each shell -> concatenate
    336 +L_out -> split by shell -> inhibit each shell -> concatenate
    337 +B_out -> split by shell -> inhibit each shell -> concatenate
    338 +```
    339 +
    340 +For one shell tier, the operation is:
    341 +
    342 +```text
    343 +magnitude = abs(shell_output)
    344 +other_mean = (sum(magnitude over shell features) - magnitude) / (width - 1)
    345 +inhibited_magnitude = relu(magnitude - strength * other_mean)
    346 +inhibited_shell_output = sign(shell_output) * inhibited_magnitude
    347 +```
    348 +
    349 +`strength` is the inhibition coefficient for that shell tier. The full-inhibition run used:
    350 +
    351 +```text
    352 +hard_kernel  = 0.00
    353 +inner_shell  = 0.35
    354 +middle_shell = 0.22
    355 +outer_shell  = 0.10
    356 +```
    357 +
    358 +The half-inhibition diagnostic used:
    359 +
    360 +```text
    361 +hard_kernel  = 0.000
    362 +inner_shell  = 0.175
    363 +middle_shell = 0.110
    364 +outer_shell  = 0.050
    365 +```
    366 +
    367 +The hard kernel is not inhibited in either setting.
    368 +
    369 +## Outward Shell Evidence Cascade
    370 +
    371 +The current code implements an outward shell-to-shell evidence path. It is not HiBaCaML consolidation.
    372 +
    373 +The current cascade direction is:
    374 +
    375 +```text
    376 +hard_kernel -> inner_shell -> middle_shell -> outer_shell
    377 +```
    378 +
    379 +For each adjacent pair, there is a learned matrix and bias:
    380 +
    381 +```text
    382 +shell_evidence_cascade_hard_kernel_to_inner_shell
    383 +shell_evidence_cascade_inner_shell_to_middle_shell
    384 +shell_evidence_cascade_middle_shell_to_outer_shell
    385 +```
    386 +
    387 +The forward pass adds:
    388 +
    389 +```text
    390 +target_shell = target_shell + scale[pair] * (source_shell @ W_pair + b_pair)
    391 +```
    392 +
    393 +Recent runs use `scale = 0.05,0.05,0.05`.
    394 +
    395 +This path is useful as shell communication, but it is opposite to the consolidation mechanism described in the paper. The paper's consolidation moves reusable mat
         erial inward, while this implemented path sends evidence outward.
    396 +
    397 +## Column LayerNorm
    398 +
    399 +If `--layer_norm_tokens` is set, each shell output is normalized independently before the shell outputs are concatenated. This is implemented in `_shellwise_layer
         norm()`.
    400 +
    401 +If `--fix_ln_gamma` is also set, gamma is scalar `1.0` and beta is scalar `0.0`. The recent runs use both flags. That removes the learned LayerNorm rescale path i
         n the stage taps, `stage4_pool`, and depth-spanning columns.
    402 +
    403 +## Column Output As A Predictive-Coding Node
    404 +
    405 +After K/L/B mixing, same-tier inhibition, outward cascade, and optional shell-wise LayerNorm, the column concatenates shell outputs:
    406 +
    407 +```text
    408 +pre_activation = concat(
    409 +    hard_kernel_output,
    410 +    inner_shell_output,
    411 +    middle_shell_output,
    412 +    outer_shell_output
    413 +)
    414 +z_mu = activation(pre_activation)
    415 +error = z_latent - z_mu
    416 +E = GaussianEnergy(z_latent, z_mu)
    417 +```
    418 +
    419 +The column is still a FabricPC node. Its latent `z_latent` is inferred during predictive-coding inference. Its parameters are updated by local gradients after inf
         erence.
    420 +
    421 +## Combiner
    422 +
    423 +`MaskedColumnCombinerNode` receives every column output, applies `support_mask`, and produces `(batch, tokens, embed_dim)`.
    424 +
    425 +For `--combiner sum`, the current recent setting, the computation is:
    426 +
    427 +```text
    428 +pre_activation = sum_i support_mask[i] * col_i
    429 +pre_activation = pre_activation / sqrt(active_count)
    430 +```
    431 +
    432 +For the current active mask, `active_count = 4`. The combiner divides the summed columns by `2.0`.
    433 +
    434 +For `--combiner attention`, which is implemented but not used in recent runs, the node learns `col_attention`, masks inactive columns with a large negative logit,
          applies softmax, and returns the weighted sum.
    435 +
    436 +## Main Readout And Auxiliary Readouts
    437 +
    438 +The main readout path is:
    439 +
    440 +```text
    441 +col_00 \
    442 +col_01  \
    443 +col_02   +--> combiner -> column_pool -> output
    444 +col_03  /
    445 +```
    446 +
    447 +`column_pool` is upstream FabricPC `AvgPool(global_pool=True)`. It averages the combiner over the token axis and outputs `(batch, embed_dim)`.
    448 +
    449 +`output` is upstream FabricPC `Linear(shape=(10,), activation=SoftmaxActivation(), flatten_input=True)`. It uses `WeightedLabelSmoothedCrossEntropyEnergy` with we
         ight `1.0` and the configured label smoothing value.
    450 +
    451 +The column teacher path is always created:
    452 +
    453 +```text
    454 +combiner -> column_pool -> column_teacher_output
    455 +```
    456 +
    457 +`column_teacher_output` is also a softmax `Linear(shape=(10,), flatten_input=True)`. Recent shell dynamics runs set `--column_teacher_weight 0.0`, so this node's
         energy does not contribute class error in those runs.
    458 +
    459 +## Per-Column Shell Direct Readout
    460 +
    461 +When `--column_shell_readout` is set, each active column also exposes each shell slice directly to the classifier.
    462 +
    463 +For one column, the pattern is:
    464 +
    465 +```text
    466 +col_c
    467 +  |
    468 +  +--> columnCC_hard_kernel_slice  -> columnCC_hard_kernel_pool  -> output
    469 +  +--> columnCC_inner_shell_slice  -> columnCC_inner_shell_pool  -> output
    470 +  +--> columnCC_middle_shell_slice -> columnCC_middle_shell_pool -> output
    471 +  +--> columnCC_outer_shell_slice  -> columnCC_outer_shell_pool  -> output
    472 +```
    473 +
    474 +`FeatureSliceNode` performs the contiguous feature-axis slice and has no learnable parameters. `AvgPool(global_pool=True)` pools the token axis. The direct shell
         readout preserves column identity and shell identity until the final classifier node.
    475 +
    476 +For the current graph with four active columns, this creates 16 shell slice nodes and 16 shell pool nodes.
    477 +
    478 +## Per-Column Shell Bridge
    479 +
    480 +When `--column_shell_bridge` is set, each active column has one bridge node receiving all four pooled shell vectors.
    481 +
    482 +For one column, the pattern is:
    483 +
    484 +```text
    485 +columnCC_hard_kernel_pool  \
    486 +columnCC_inner_shell_pool   \
    487 +columnCC_middle_shell_pool   +--> columnCC_shell_bridge -> output
    488 +columnCC_outer_shell_pool   /
    489 +```
    490 +
    491 +`columnCC_shell_bridge` is an upstream FabricPC `Linear(shape=(embed_dim,), activation=IdentityActivation(), flatten_input=False)`. Because `flatten_input=False`,
          each input edge is transformed along its last feature axis into `embed_dim`, and the transformed shell inputs are summed.
    492 +
    493 +This bridge is a predictive-coding latent with Gaussian energy. It is not just a readout-time concatenation. During inference, its latent participates in the grap
         h energy and can send gradient contributions back to its shell-pool inputs.
    494 +
    495 +## Optional Bypass Path
    496 +
    497 +The optional bypass path is controlled by `--bypass_columns`:
    498 +
    499 +```text
    500 +stage4_out -> bypass_pool -> output
    501 +```
    502 +
    503 +Recent shell dynamics runs did not use the bypass. Earlier experiments used it to separate direct backbone evidence from column-mediated evidence. The current gra
         ph builder still supports it.
    504 +

    577 +## Predictive-Coding Mechanics
    578 +
    579 +Every node follows the FabricPC `NodeBase.forward()` contract:
    580 +
    581 +```text
    582 +inputs and params -> pre_activation -> z_mu
    583 +error = z_latent - z_mu
    584 +E = energy(z_latent, z_mu)
    585 +```
    586 +
    587 +The universal node state fields are defined by FabricPC `NodeState`:
    588 +
    589 +```text
    590 +z_latent
    591 +z_mu
    592 +error
    593 +energy
    594 +pre_activation
    595 +latent_grad
    596 +```
    597 +
    598 +The graph is static. `GraphStructure` stores nodes, edges, task map, topological order, and config. `GraphParams` stores node-local weights and biases.
    599 +
    600 +### Training Clamps
    601 +
    602 +During training, FabricPC maps batch dictionary keys to nodes through `TaskMap`.
    603 +
    604 +The current depth-spanning graph always maps:
    605 +
    606 +```text
    607 +x        -> input
    608 +y        -> output
    609 +column_y -> column_teacher_output
    610 +```
    611 +
    612 +`ColumnTeacherTargetLoader` duplicates the one-hot CIFAR-10 label from `y` into `column_y`. If shell teacher heads are active, it also duplicates `y` into the she
         ll target keys.
    613 +
    614 +This means during training:
    615 +
    616 +```text
    617 +input.z_latent                 is clamped to x
    618 +output.z_latent                is clamped to y
    619 +column_teacher_output.z_latent is clamped to column_y
    620 +```
    621 +
    622 +If a teacher energy weight is zero, the node can still be clamped but its weighted cross-entropy energy contributes zero.
    623 +
    624 +### State Initialization
    625 +
    626 +FabricPC graph construction defaults to `FeedforwardStateInit()` when no custom initializer is supplied. The graph builder sets this default in `graph_constructio
         n.py`.
    627 +
    628 +`FeedforwardStateInit` first initializes all `z_latent` tensors from their node latent initializers and overlays clamps. It then walks the graph in topological or
         der. For non-clamped internal nodes, it computes `z_mu` and sets `z_latent = z_mu` before inference begins.
    629 +
    630 +### Inference Loop
    631 +
    632 +The current graph uses `InferenceSGDNormClip`:
    633 +
    634 +```text
    635 +eta_infer = args.eta_infer
    636 +infer_steps = args.infer_steps
    637 +max_norm = args.infer_max_norm
    638 +```
    639 +
    640 +Recent runs used:
    641 +
    642 +```text
    643 +eta_infer = 0.1
    644 +infer_steps = 40
    645 +max_norm = 1.0
    646 +```
    647 +
    648 +For each inference step, FabricPC does:
    649 +
    650 +```text
    651 +1. zero every node's latent_grad
    652 +2. run nodes in graph order
    653 +3. for each node, compute z_mu, error, energy
    654 +4. use autodiff to compute:
    655 +     dE/d(node z_latent)
    656 +     dE/d(each input edge latent)
    657 +5. accumulate latent_grad into the node and its input source nodes
    658 +6. update every unclamped z_latent:
    659 +     grad_norm = L2 norm over non-batch axes
    660 +     clipped_grad = grad * min(1, max_norm / (grad_norm + eps))
    661 +     z_latent = z_latent - eta_infer * clipped_grad
    662 +```
    663 +
    664 +Clamped nodes are not updated in the inference step.
    665 +
    666 +### Local Parameter Learning
    667 +
    668 +After inference, `get_graph_param_gradient()` computes local weight gradients with `compute_local_weight_gradients()`.
    669 +
    670 +For each node, FabricPC gathers the final inferred input latents, runs the node's own forward computation, and uses `jax.value_and_grad()` on that node's energy w
         ith respect to that node's parameters. This is local in the sense that the parameter gradient for one node is computed from that node's final inputs, latent, pred
         iction, and energy. The optimizer then applies those gradients through Optax AdamW.
    671 +
    672 +The current training script uses:
    673 +
    674 +```text
    675 +optax.warmup_cosine_decay_schedule
    676 +optax.adamw
    677 +weight_decay = args.weight_decay
    678 +```
    679 +
    680 +Recent runs used `lr = 0.005` and `weight_decay = 0.01`.
    681 +
    682 +### Evaluation
    683 +
    684 +During evaluation, FabricPC clamps only `x` to `input`. It does not clamp `y` to `output`. The output node is terminal and unclamped, so FabricPC sets `output.z_l
         atent = output.z_mu` and zeroes its energy. Accuracy is computed from `argmax(output.z_mu)` against the batch labels.
    685 +
    686 +This is why evaluation energy is not the classifier loss. Evaluation accuracy is the relevant metric for CIFAR classification.

    739 +
    740 +8. Per-column shell bridge.

    747 +
