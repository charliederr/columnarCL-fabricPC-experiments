• Assuming the run is the current 10-column bridge-only path, the largest thing being left out is the paper’s controller/certificate loop. We have a
  predictive-coding column substrate, but we do not yet have the full HiBaCaML algorithm that decides which columns should participate, which
  internal material should be protected, and which shell content should move inward or outward.

  Current Pipeline
  The code currently does this:

  image -> predictive-coding ResNet backbone -> stage taps -> fixed active columns -> K/L/B shell computation -> shell-preserving composer plus
  bridge/context paths -> CIFAR-10 output

  The implemented column mechanics are real: hard_kernel, inner_shell, middle_shell, and outer_shell slices are defined in columnarCL-fabricPC-
  experiments/columnar_cl_fabricpc/columns/depth_spanning_column.py:77, and each column has K, L, and B pathways in columnarCL-fabricPC-experiments/
  columnar_cl_fabricpc/columns/depth_spanning_column.py:264. The shell-preserving composer is in columnarCL-fabricPC-experiments/
  columnar_cl_fabricpc/columns/accuracy_nodes.py:428. The outer-shell context and shell bridge readout paths are wired in columnarCL-fabricPC-
  experiments/scripts/train_cifar10_depth_spanning.py:2371.

  What Is Left Out

  1. Top-level probabilistic controller.
     The paper’s Psi is the top-level controller that selects the active support S_t, meaning the subset of columns used for context or task t. We
     currently use a fixed support mask from command-line settings. The composer masks and attends over whatever columns are already active; it does
     not choose a support by evidence, context, or certificates.

  2. Teacher-first one-swap support search.
     The paper’s teacher T is a counterfactual evaluator: it tries swaps such as “remove active column a_out, add inactive column a_in,” measures an
     audited objective, and accepts the swap only if it improves. Our “teacher” heads are auxiliary class losses, not counterfactual support
     teachers.

  3. Internal certificates.
     The paper wants each column to emit certificate values such as shared-abstraction mass, specificity load, saturation pressure, demotion
     pressure, and similarity signatures. We log shell norms, lesions, attention weights, and route ablations, but those diagnostics are not emitted
     as a certificate vector and are not used by a controller.

  4. True hard-kernel protection.
     We have a hard_kernel feature slice. We do not yet make it non-prunable, freeze it after consolidation, protect it with posterior precision, or
     require stronger evidence before it changes. It is still trainable ordinary model state.

  5. Promotion, demotion, and pruning.
     The paper’s radial shell semantics require outer-to-inner promotion when content becomes reusable, inner-to-outer demotion when content becomes
     task-local or stale, and outside-in pruning. We have same-tier inhibition and outward evidence cascade, but no audited shell movement or
     pruning.

  6. Full Bayesian two-level state.
     FabricPC gives us predictive-coding latent inference, but we do not yet have the paper’s two-level Bayesian structure: a posterior over column
     supports plus internal probabilistic states estimating reuse, specificity, and uncertainty inside each column.

  7. CIFAR-scale sparse column regime.
     The paper recommends Ncol = 40, Nshared = 4, and knonshared = 5, giving 9 active columns per example. We are currently testing 10 columns with
     all columns active. That helps diagnose capacity, but it does not test sparse support selection.

  8. Shallow CIFAR stem.
     The paper recommends a shallow shared visual stem before columns. Our current pipeline uses a deeper ResNet-style predictive-coding backbone and
     taps stages into columns. That gives better visual features, but it shifts more representational burden into the backbone than the paper’s
     proposed CIFAR architecture.

  9. Hierarchical auxiliary targets.
     The paper suggests fine-scale patch tokens with quadrant and global auxiliary targets tied by consistency losses. We have stage taps and a
     global pool, but not explicit quadrant/global consistency objectives.

  10. Continual-learning retention objective.
     By design, we are currently doing plain CIFAR-10. So we do not yet have task contexts, task-local heads, worst-old-task retention, support churn
     penalties, or Split-CIFAR forgetting measurements.

  The practical summary is: we have built much of the column body, but not yet the full columnar control system. The next faithful step after this
  run is probably to add a small controller/certificate/audit loop on plain CIFAR-10, before moving to Split-CIFAR.
